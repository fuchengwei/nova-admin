# 接口权限多主体授权设计

## 背景

当前接口权限仅通过 `sys_role_api_permission` 关联角色。用户必须先获得角色，再间接获得接口权限，无法对单个用户直接授权，也没有清晰的“所有已登录用户可访问”配置。

## 目标

为每个已注册接口权限提供三种可组合的授权方式：

- 公开访问：所有已登录用户都能访问；
- 角色授权：拥有任一指定角色的用户可以访问；
- 用户授权：被直接指定的用户可以访问。

最终访问规则为：

```text
public_access = true
OR 用户拥有任一指定角色
OR 用户在直接授权用户列表中
```

三种方式可以同时存在。关闭公开访问且角色、用户列表均为空时，接口权限对所有用户拒绝。

## 数据模型

在 `sys_api_permission` 增加：

```text
public_access SMALLINT NOT NULL DEFAULT 0
```

新增用户直接授权关系表：

```text
sys_user_api_permission (
    user_id           BIGINT NOT NULL,
    api_permission_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, api_permission_id)
)
```

保留现有 `sys_role_api_permission`，不把公开访问伪装成特殊角色。关系表删除采用按权限整体替换，保存请求中的最终角色和用户列表，避免产生孤儿关联。

## 后端接口

将现有角色保存能力扩展为统一授权保存接口，请求包含：

```json
{
  "permission": "system:user:export",
  "publicAccess": false,
  "roleIds": ["2"],
  "userIds": ["7", "8"]
}
```

响应仍使用项目统一的 `R<T>` 格式，并在 Controller 上补齐 `@Operation`、`@Schema` 注解。

读取接口权限时，DTO 同时返回 `publicAccess`、`roleIds`、`userIds`。用户候选项复用现有启用用户查询能力，前端只展示启用用户。

## 权限加载与缓存刷新

`UserDetailsServiceImpl` 加载用户权限时，将以下三类权限合并到 `LoginUser.permissions`：

1. 用户角色关联的接口权限；
2. 用户直接关联的接口权限；
3. `public_access = 1` 的接口权限。

现有 `@PreAuthorize("hasAuthority(...)")` 无需逐个改造，公开访问只改变权限集合来源，仍要求请求先通过认证。因此“公开访问”不等于匿名访问。

保存授权时计算受影响用户：

- 角色关系变化：刷新变更前后角色对应的用户；
- 用户关系变化：刷新变更前后用户列表；
- 公开开关变化：刷新全部启用用户。

事务提交后发布现有 `AuthorizationChangedEvent.permissionsOf(...)`，保证已登录会话实时重建权限缓存。

## 前端交互

接口权限配置弹窗改为三段式但可组合的表单：

- “登录用户可访问”开关；
- “授权角色”多选；
- “授权用户”多选。

保存时一次提交三类授权。表格增加公开状态、已授权用户摘要；角色和用户均没有授权时显示未配置提示。所有文案同步 `zh.ts` 与 `en.ts`。

## 错误处理与边界

- 只接受启用的角色和用户，提交已禁用或不存在主体时返回参数错误；
- 未注册接口不能保存授权；
- 重复的角色或用户 ID 在服务层去重；
- 清空全部授权是合法操作，表示暂时无人可访问；
- 超级管理员继续拥有现有超级管理员权限，不受普通授权配置影响。

## 测试

后端新增或扩展 JUnit5 测试覆盖：

- 公开权限被加入登录用户权限集合；
- 角色授权和直接用户授权分别生效；
- 角色与用户授权并集生效；
- 清空授权后权限被移除；
- 公开开关变更刷新全部启用用户；
- 非法角色、用户和未注册权限被拒绝。

前端通过类型检查和构建验证授权表单、DTO 字段和 i18n key 同步；若仓库测试框架仍未配置，则在交付说明中明确测试缺口。

## 非目标

- 不支持匿名访问；
- 不重写现有菜单权限和角色菜单授权模型；
- 不引入通用多态授权主体表；
- 不改变接口扫描和 `@PreAuthorize` 注解的发现机制。
